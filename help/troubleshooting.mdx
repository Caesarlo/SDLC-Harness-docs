## Command not found or incorrect Node.js version

Confirm that Node.js is at least version 22:

```bash
node --version
npx @caesarlo/sdlc-harness --help
```

Running `sdlc-harness` directly requires the CLI to be installed. Otherwise, use the full npx package name.

## `init` reports file conflicts

Prefer `adopt` for an existing repository. Use `init --force` only after confirming that the listed files can be overwritten. The command calculates all conflicts first and does not leave a partially initialized skeleton.

## `adopt` skips existing files

This is expected. It never overwrites existing files. Review each item in the skipped list. When you need Harness content in one of those files, merge it manually instead of rerunning the command and expecting an overwrite.

## `[agents-onboarding]` fails

The repository already had `AGENTS.md`, so adopt wrote `AGENTS.sdlc-harness.md`. Add an explicit reference in the existing `AGENTS.md` so new Agent sessions can discover the sidecar.

## A feature cannot be started or claimed

```bash
npx @caesarlo/sdlc-harness status
```

[View the `status` command →](/reference/command-repository#status)

Check whether the feature is `not_started`, all dependencies are `passing`, an active claim exists, or the owner has reached the WIP limit. `claim --next` selects only ready features.

## A claim has expired

The original owner can renew it. Another owner can only take over an expired claim explicitly:

```bash
npx @caesarlo/sdlc-harness claim <feature-id> --takeover-expired --owner bob
```

[View expired takeover arguments →](/reference/command-claim#takeover-expired)

An active claim cannot be taken over. If the original work is still in progress, the original owner should run `claim renew`.

## `verify` refuses to run in Team mode

Team mode does not claim automatically:

```bash
npx @caesarlo/sdlc-harness claim <feature-id> --owner alice
npx @caesarlo/sdlc-harness verify <feature-id>
```

Argument reference: [Claim a feature](/reference/command-claim#claim) · [Run verification](/reference/command-evidence#verify)

Solo mode also refuses to compete with another owner's active claim.

## Manual verification cannot run

`verify` does not treat a manual description as a shell command. Use:

```bash
npx @caesarlo/sdlc-harness evidence manual <feature-id> \
  --verification 1 --result passed --notes "Actual environment and observed result"
```

[View `evidence manual` arguments →](/reference/command-evidence#manual)

## `verify` passes but `feature complete` fails

Check these conditions:

- The current owner still holds an active claim.
- All dependencies are `passing`.
- Every verification item has passing evidence for the current commit.
- A passing review exists after the latest verification.
- The reviewer differs from the claim owner.

Verification at an old commit cannot establish results for code changed afterward. Run `verify` again, then record another review.

## `[pass-gate]` or a passing regression

Do not directly change an old feature from `passing` to another status. Create a new feature for the regression or new requirement. CI should fetch enough Git history and set `HARNESS_BASE_REF` or provide `GITHUB_BASE_REF`.

## `[stage-gate]` or `[traceability]` fails

```bash
npx @caesarlo/sdlc-harness traceability
```

[View the `traceability` command →](/reference/command-repository#traceability)

Use paths to files that actually exist in the repository and stable IDs, for example:

```json
"source_refs": ["docs/product/requirements.md#FR-1"]
```

Also check the complete requirement, story, AC, feature, and verification chain. A file path merely existing is not enough.

## Artifact approval is invalid

Approval is bound to a content hash. After the file changes, confirm the new content and run:

```bash
npx @caesarlo/sdlc-harness evidence approval <artifact> \
  --actor <id> --summary <text>
```

[View `evidence approval` arguments →](/reference/command-evidence#approval)

## A workspace cannot be removed or prune skips it

The tool protects uncommitted or unpushed work and skips workspaces with active claims. Commit, push, or release the claim first. Use `--force` only when you explicitly accept losing content.

## GitHub check shows `UNKNOWN`

The current `gh` token lacks permission to read administrative configuration. `UNKNOWN` means the configuration cannot be confirmed; it is neither a failure nor a pass. Check again with a token that has sufficient permission.

## CI evidence cannot be imported

Confirm that the run ID belongs to the target repository, has completed, and has a successful conclusion. If the repository cannot be inferred from `origin`, pass `--owner` and `--repo` explicitly.

## `env check` fails

```bash
npx @caesarlo/sdlc-harness env
```

[View the `env` command →](/reference/command-environment#env)

Copy the actual failing command and run it by itself from the repository root. Check dependencies, environment variables, and service prerequisites. Because `env check` stops after the first failure, run it again after the fix to discover later issues.

## `session close` exits nonzero

This means `validate` or a configured environment command failed. Uncommitted files are reported but do not cause a nonzero exit by themselves. Look above for the specific `[validator]` or env FAIL line.

## Feedback log audit fails

Prefer `feedback log` for well-formed entries. Severity can only be S1-S4, and disposition can only be one of the four allowed values. Deferred and Declined entries require a reason.
