## Does it replace a test framework?

No. You continue to use project tools such as Jest, Vitest, pytest, and Playwright. SDLC Harness executes declared commands, records their results, and checks completion evidence.

## Does it replace a project management tool?

No. `feature_list.json` provides delivery status close to the code that Agents can act on. Teams can still use Linear, Jira, or similar tools for higher-level planning, but should clearly decide which side is the source of truth for development execution status.

## Does `validate` run tests?

No. `verify` runs feature verification, `env check` runs project-level environment commands, and `validate` only audits repository state and evidence.

## Why can't I complete a feature after `verify` passes?

Passing tests is only one condition. You also need an active claim, passing dependencies, evidence for every verification item at the current commit, and a passing review recorded after the latest verification by a different reviewer.

## Why does Solo mode still have claim fields?

A claim is not a file lock and cannot prevent arbitrary concurrent writes. It coordinates same-feature work among participants that follow the protocol. Claim-aware operations such as `verify` and `feature complete` enforce that coordination. Solo mode only hides routine operations: `verify` creates and releases a temporary claim as needed.

## Can multiple Agents use the same owner?

Yes. Use different actors to distinguish sessions. The WIP limit is calculated by owner, and each feature can still have only one claim. An independent reviewer must use an identity different from the claim owner.

## Can I edit `feature_list.json` manually?

You can maintain planning fields, but use the CLI for claim, workspace, evidence, blocker, and status transitions. `new-feature --input` is the safe non-interactive entry point for an Agent to create a feature.

## Which files should I commit?

Commit the protocol, configuration, `feature_list.json`, requirements, ADRs, workflows, Git hooks, CI templates, and `.harness/events/*.jsonl`. Do not commit `.harness/last-validated-features.json` or `.worktrees/`.

## A feature is already passing but needs a change. What should I do?

Create a new feature describing the regression, enhancement, or migration. The default monotonicity rule prevents an old feature from silently regressing and preserves an explainable historical conclusion.

## Can a library with no deployment target use it?

Yes. Set `deploymentMode: "none"`, then choose `observabilityMode: "feedback-only"` or `"none"` depending on whether you need a feedback log.

## Is a claim a distributed lock?

No. It is an auditable lease stored in Git state. It coordinates same-feature work among participants that follow the protocol; it cannot lock files or prevent arbitrary writes. For cross-machine use, run `claim --push` and synchronize the remote promptly, while accepting that Git does not provide real-time locking.

## Can it prove that requirements are correct?

No. It can show checkable relationships among requirements, features, acceptance criteria, and evidence. Product judgment, requirement quality, and test sufficiency remain the responsibility of people and teams.
