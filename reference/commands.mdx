所有命令都在目标仓库根目录运行。本文省略重复的 `npx @caesarlo/sdlc-harness` 前缀；未安装 CLI 时请加上该前缀。

```bash
npx @caesarlo/sdlc-harness --help
```

## 初始化

| 命令 | 作用 |
| --- | --- |
| `init [--force]` | 生成完整协议；遇到已有文件默认停止并列出冲突 |
| `adopt` | 只插入缺失文件；已有 `AGENTS.md` 时生成 sidecar |

`--force` 只应在确认允许覆盖 `init` 报告的冲突时使用。

## 仓库状态与审核

| 命令 | 输出与退出状态 |
| --- | --- |
| `validate` | 运行全部治理检查；失败输出分类错误并返回非零 |
| `status` | 输出功能、审批、追溯和下一步的 JSON 摘要 |
| `traceability` | 输出完整追溯矩阵；存在实际缺口时返回非零 |

## 规划

```bash
sdlc-harness new-milestone
sdlc-harness new-feature
sdlc-harness new-feature --input <repo-relative-json-file>
```

前两者交互创建。`--input` 适合 Agent 自动化，文件必须位于仓库内，且不能注入 claim、evidence、workspace 或完成状态。

## 功能生命周期

```bash
sdlc-harness feature start <feature-id> [--owner <name>] [--actor <id>] [--ttl <minutes>]
sdlc-harness feature complete <feature-id> [--owner <name>]
sdlc-harness feature block <feature-id> --reason <text> [--owner <name>]
sdlc-harness feature reopen <feature-id> [--actor <id>]
```

| 子命令 | 状态变化 |
| --- | --- |
| `start` | 检查 ready、依赖和 WIP，认领并进入 `in_progress` |
| `complete` | 要求有效 claim、依赖、当前 commit 验证和后续独立 review，再进入 `passing` |
| `block` | 记录 blocker、释放 claim并进入 `blocked` |
| `reopen` | 清除 blocker，从 `blocked` 返回 `not_started` |

## 验证与证据

```bash
sdlc-harness verify <feature-id>
sdlc-harness evidence manual <feature-id> \
  --verification <1-based-index> --result <passed|failed> \
  --notes <text> [--actor <id>]
sdlc-harness review record <feature-id> \
  --reviewer <id> --summary <text> [--result passed|failed]
sdlc-harness evidence approval <artifact> --actor <id> --summary <text>
sdlc-harness evidence import <feature-id> --ci-run <run-id> \
  [--owner <github-owner>] [--repo <github-repo>]
```

- `verify` 实际运行自动 verification，并记录 test 证据。
- `evidence manual` 只能绑定声明为 manual 的验证项。
- `review record` 绑定当前 commit；完成门禁要求 reviewer 不同于 claim owner。
- `evidence approval` 记录与制品内容哈希绑定的项目级审批。
- `evidence import` 只接受 GitHub 已完成且成功的真实 run。

## claim 与租约

```bash
sdlc-harness claim <feature-id> [--owner <name>] [--actor <id>] [--ttl <minutes>]
sdlc-harness claim --next [--owner <name>] [--actor <id>] [--ttl <minutes>]
sdlc-harness claim renew <feature-id> [--owner <name>] [--ttl <minutes>]
sdlc-harness claim <feature-id> --takeover-expired [--owner <name>] [--actor <id>]
sdlc-harness claim <feature-id> --push [--remote origin] [--branch main]
sdlc-harness release <feature-id> [--owner <name>]
```

`--next` 选择依赖已 `passing`、未被有效认领的 `not_started` 功能，并按 priority 和列表顺序排序。默认租约为 120 分钟。`--takeover-expired` 只允许接管已过期 claim。`release` 将 `in_progress` 恢复为 `not_started`。

<Note>
  Solo 模式通常无需手动 claim；`verify` 会按需为 `defaultOwner` 临时认领并释放。Team 模式必须事先持有有效 claim。
</Note>

## workspace

```bash
sdlc-harness workspace create <feature-id> [--base <branch>]
sdlc-harness workspace status
sdlc-harness workspace remove <feature-id> [--force]
sdlc-harness workspace prune [--force]
```

create 为已认领功能创建 `.worktrees/<id>` 和 `feature/<id>` 分支。remove 默认拒绝删除含未提交或未推送工作的 workspace。prune 只考虑 claim 已释放或过期的 workspace，绝不触碰活跃 claim。

## GitHub provider

```bash
sdlc-harness provider github check \
  [--owner <github-owner>] [--repo <github-repo>] [--branch main]
```

未显式指定仓库时从 `origin` 推断。结果为 `PASS`、`FAIL` 或因 token 权限不足而无法确认的 `UNKNOWN`。

## 项目环境

```bash
sdlc-harness env
sdlc-harness env check
```

`env` 列出已配置命令。`env check` 依次运行已配置的 `bootstrap`、`verify`、`e2e`、`health`，第一次失败后停止并返回非零。

## 会话收尾

```bash
sdlc-harness session close
```

只读运行 `validate`、环境检查并汇总 Git 与功能状态。它不会自动提交、释放 claim 或清理 workspace。

## 反馈

```bash
sdlc-harness feedback log \
  --source <text> --severity <S1|S2|S3|S4> \
  --observation <text> \
  --disposition <Actioned|Deferred|Declined|Monitoring> \
  [--detail <text>] [--date <YYYY-MM-DD>]
```

新条目写入反馈日志顶部。`Deferred` 和 `Declined` 必须说明原因。

## 通用默认值

| 参数 | 默认值 |
| --- | --- |
| `--owner` | `harness.config.json.defaultOwner` |
| `--actor` | 未指定时按相应命令的 owner/默认 owner 处理 |
| `--ttl` | 120 分钟 |
| `--remote` | `origin` |
| `--branch` | `main` |
| `--base` | `main` |

<Warning>
  `init --force` 和 `workspace ... --force` 可能覆盖文件或丢弃未保存工作。先阅读命令输出的准确目标和风险。
</Warning>
